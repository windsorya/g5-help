推薦：B

不收斂的根本原因，是讓多個寫入者各自修改記憶體快照，再覆寫整份存檔；`r／BASE／DIRTY` 沒有把「讀取、判斷、寫入」變成不可交錯的操作，`sync.js` 又另有直接替換資料的入口。另一方面，存檔、未提交進度與畫面切換混在一起，所以即使解決儲存競爭，延後 callback 仍可能清掉另一篇畫面。

**我推薦 B，並把「只允許一個分頁練習」正式定為產品規則。**孩子通常只用一頁，沒有必要為罕見的同時練習承擔完整合併協定。若未來明確要支援兩頁同時作答，再採 A，並設計題次操作如何合併。

B 必須包含下列設計，不能只在 `save()` 外面加一把鎖：

1. **取鎖後才啟用作答及任何寫入。**持有整個工作階段的同名 exclusive lock；未取得者顯示「已在另一個分頁開著，請回到原分頁練習」。唯讀頁不得因初始化、教學完成、搬家、備份或同步而寫入。Web Locks 的鎖生命週期由 callback 的 Promise 決定。[Web Locks 規範](https://www.w3.org/TR/web-locks/)

2. **所有 `g5help.v1` 寫入共用入口。**涵蓋 app、同步、壞資料復原、舊資料搬家，以及其他載入 `sync.js` 的頁面。持鎖頁內再序列化操作，避免 app 與 sync 各自持有一份可覆寫的真相。`g5sync.meta` 是跨 key 共用物件，其更新也要序列化，避免 baseline 互蓋。

3. **背景下載不直接改存檔或 reload。**孩子開始操作後，下載結果只成為待套用候選。到首頁明確套用時，重新檢查本地內容、雲端版本及未存進度；先停止舊畫面的操作，再備份、替換、處理 baseline，最後才由統一入口決定 reload。選擇雲端後若本地又有修改，原選擇失效。

4. **修改先標記未提交，存成功才清除。**每篇未存進度獨立保留；任何失敗出口、storage 事件、切篇及同步，都不能把它洗掉。顯示持續可見的「尚未存好，請先不要關閉」；不得顯示整份最新進度已同步。儲存恢復後重試，不重複計分。

5. **讀取沒有寫入副作用；復原沒有先刪再建的空窗。**壞原文備份成功並核對後，才以新值替換主 key；備份失敗就保留原文。讀取拋錯不等於沒有紀錄，不得據此寫入空白資料。

6. **交接與畫面 callback 都有世代。**交出寫入權前停用操作、使舊回應失效；新持有者先重讀，再啟用。延後 callback 綁定篇 id 與畫面世代。背景暫停不靠逾時強行接管，也不用 `steal`。

舊版頁面不遵守新鎖，是 B 的上線前提限制：必須一起更新並退出舊寫入端；若無法排除舊版長時間共存，就需要新的存檔 namespace 與相應同步遷移，成本會提高。
