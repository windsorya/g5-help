## 實作對照（src/upload.js；根目錄 upload.js 逐字相同）

| 設計要求 | 實作 |
|---|---|
| familyCheck 只失效、不發請求 | `familyCheck()`：讀 localStorage；碼變了就家庭版本 `FREV`+1、作廢查詢／撤回確認／撤回／上傳、清空清單；只回傳「換了沒」 |
| 單一查詢協調器 | `refresh()` 是唯一發 `mine` 的地方；`ACTIVE` 在途且未過期就合併（手動、自動一樣） |
| 回應四重檢查 | 查詢：owner（`live()`）、家庭版本、查詢世代 `GEN`、期限；撤回：owner、操作身分（`WD_OP === op`）、家庭版本、期限；上傳：owner、操作身分、家庭版本 |
| 撤回、上傳各持 operation token | `WD_OP`、`UP_OP`；只有「目前那一筆」能解鎖、改訊息、清草稿 |
| stop 終結全部 | `stop()`：清兩個 interval、撤回確認計時器、查詢與撤回期限計時器；拆 storage／visibilitychange／pageshow；在途查詢 abort；撤回、上傳失去資格；可重複呼叫 |
| 同容器重掛終結前一個 owner | 容器上的 `__g5upload` 記目前的 handle，`mount()` 先呼叫前一個的 `stop()`；DOM 一律從自己的根節點找（舊閉包碰不到新節點） |
| post() 檢查 HTTP 與形狀 | 非 2xx、非 JSON、非物件都丟錯；清單另要 `ok:true` 且 `items` 是陣列（`mineItems`） |
| 90 秒期限 | `DEADLINE_MS = 90000`，`// cap-why:` 寫在常數旁；回應入口、發送前（`refresh`）、回前景（visibilitychange／pageshow）都核對；先邏輯結束再 abort |

公開 API 不變：`G5Upload.mount(sel, {subject, site, units})` 回傳 `{reload, stop}`；另匯出純函式（`parseReply`、`mineItems`、`withdrawOutcome`、`withdrawMessage`、`familyOf`、`dropWithdrawn`、`DEADLINE_MS`）給 node 測試。

## 設計沒寫死、這次採用的做法（可推翻）

1. `reload(auto)` 的 `auto` 保留相容但不再區分：手動與自動都與在途查詢合併（設計 (d) 的假設：reload 是「打開時重抓」）。
2. 撤回結束（成功、明確失敗、還沒確認）都重查一次清單，讓畫面對上伺服器現況；撤回 POST 一律不自動重送。
3. 撤回網路失敗／逾時／回應殘缺：「撤回結果還沒確認（可能沒有網路）。清單重新整理後，這題如果還在，可以再撤回一次。」（後端對已撤回的再撤一次回 ok，重按無害）
4. 上傳不設期限（沿用原行為），出口是換家庭、stop、重掛：換家庭當下解鎖輸入，提示「後面的照片沒有送出；前面已送出的 N 張不受影響」，不宣稱取消。
5. 按「送出」那一刻才發現家庭碼剛變：這一下不送，請家長確認後再按（不沿用、也不改送新家庭）。
6. AbortController 只用在清單查詢；撤回、上傳是寫入，中斷等待不代表伺服器沒做，所以不 abort，只讓遲到的回應失去資格。
7. 設計 (c) 首選「同步碼寫入端發變更事件」：寫入端在 `src/sync.js`，不在這次範圍，仍以 2 秒輪詢補救＋storage／visibilitychange／pageshow＋每個入口重讀家庭碼。
