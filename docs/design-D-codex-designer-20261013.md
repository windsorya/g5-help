**3. 推薦與有限驗收矩陣**

**A 推薦 A1，搭配 A3 驗收。**

改動核心是：**每個家庭／key 同時只有一筆尚未確認的上傳，而且送出前就已經保存。**

建議 checkpoint 包含：

```text
version、codeHash、key
baseline：已確認的 rev、內容 hash
pending：baseRev、實際送出的完整 payload、payload hash
```

`baseline` 與 `pending` 放在同一筆可原子替換的儲存紀錄。難題站採獨立 namespace，不把其他站的 metadata 當成可任意改版的私有資料。

操作規則：

1. **先保存並讀回 pending，才可送 PUT。**寫入或讀回失敗就不送。
2. pending 未解決前，重試同一份 `baseRev＋payload`。孩子仍可繼續答，新進度照常存入 app，但不改寫 pending。
3. 首次啟用、重開頁、GET、PUT conflict 都進同一個恢復判斷：
   - 雲端仍是 pending 的基準版本及內容：重送原 pending。
   - 雲端是 `baseRev + 1`，且完整內容等於 pending：確認這份內容已提交，保存新 baseline、清 pending。
   - 其他有效版本變化：按真正分歧處理；壞回應、讀取失敗則維持「待確認」，不能叫作兩台分歧。
4. 確認完舊 pending，才從本機最新資料建立下一筆；baseline 永遠對應已確認的 payload。
5. 保留設計 C：同步不能直接改 `g5help.v1`；下載替換仍經 `canReplace／accept`。
6. 舊版沒有 pending、又出現雙邊不同的情況，無法事後證明是哪台寫的。保留兩份並說明「無法確認」，不自動覆蓋，也不冒稱修復完成。
